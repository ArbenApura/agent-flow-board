# Browser checks: the bridge reference

This file is the reference for browser checks. The rules that always apply (what triggers a check, when to skip, the safety rules, the one stop) are in the `flow` text, section 3 step 5a. Read this file before the first check or the first approval request of a run, and again when a run ends with a code or a refusal.

Everything below that installs, upgrades or connects the bridge, registers a folder, asks for an approval or opens a sign-in window is for a check the user asked for. A yes to the hand-over line "set up checks" (`flow` section 2, step 7) counts as asking, for the steps of "Set up checks" below only. The automatic check and the phase peek of a visible change never do any of it: it runs only when the bridge, the registration and the saved sign-in are already there (`flow` section 3 step 5a).

Checks run through the bridge: `agent-flow-board check ...` (the npm package `@agent-flow-board/bridge`). Work in the project's repo folder. When the command is not installed and the person asked for a check, install it first (`npm install -g @agent-flow-board/bridge@latest`). A run is taken by whichever tool serves the project, so never run two tools for one project at the same time. A machine that still has the old standalone `afb-checks` folder moves over with `agent-flow-board check import-legacy --from <that folder> --org <slug> --dry-run` (read only), then the same command without `--dry-run`, and its worker is stopped before the bridge serves the project.

## How a run works

1. `agent-flow-board check doctor --fix --json` once, and at the start of every run. It installs the browser on first use, repairs what it can and lists each problem left with its `next` step. Do each `next`, then run it again until `problems` is empty or the next step is the one stop. `check status --json` shows projects, every connected board, the worker's slots, the service and its `home` folder.
2. Connect once per organisation (nobody types a code): `runner_status` says no tool is connected, or doctor lists a board problem with a connect command. Start `agent-flow-board check connect --server <board address> --org <org slug> --json` in the background (the address and the slug are in `runner_status`), read its first line (`userCode` and `verifier`, never print them), call `tool_connection_approve` with both (only a code this bridge started is accepted, and the manage permission is needed), and wait for the `connected` line. Then start the worker yourself (on Windows `agent-flow-board check service install`, which starts it now and at every sign-in; on macOS or Linux `agent-flow-board check watch` in the background), run `check doctor --fix --json`, and call `runner_status` again. If `tool_connection_approve` answers that the token lacks the manage permission, that one thing is the owner's: say once, in one line, and carry on with everything that does not need the bridge. Connecting adds this organisation next to the others and never replaces one: ask `runner_status` on the connection of that organisation (its tools are `mcp__afb-<org-slug>__...`). To forget one: `check disconnect --server <board address> --org <slug>`. Add `--project KEY` to serve one project only.
3. Write the check script to `~/.agent-flow-board/checks/scripts/<org>/<ITEM-REF>/<CHECK-KEY>.mjs` (the `home` folder that `check status --json` names, then `scripts/`). It is never inside the repo. A check gets `page`, `step`, `shot`, `expect`, `log` and `baseUrl`, and nothing else. Save the same text on the board with `check_save` (item, check, a short title, script, target `preview`); it creates the check when the key is new. For a new check use the next free key: `C` and one more than the highest `C` number in `item_get` (`fields: ["checks"]`). The title of an automatic check starts with `Auto`.
4. Ask `runner_status` for the project. If a bridge is online, go on. If not, its `agentAction` lists steps for you: do them and ask again.
5. Ask for the run and wait in one call with `check_run` (`item`, `check`, `target` `preview`, `step` the plan step it closes when there is one, `wait` 45; if `finished` is false, call `check_wait` with the run id until it is), while the worker or the installed service is running. Or in the repo folder: `agent-flow-board check run <ITEM-REF> <CHECK-KEY> --server <board address> --org <org slug> [--step <key>] [--registration NAME]`. The bridge asks the board for the run, claims that run only, builds a private copy of the repo, previews it on a free port (never a port the repo rulebook keeps for a server the person runs, nor their database), runs the script in a sandboxed Node child, uploads the pictures and reports. `check run` exits 0 on a pass, 1 on a fail and 2 when it could not run; the last line is `RESULT <path>`. If you already asked with `check_run`, pass `--run <id>`.
6. The repo needs `.afb-checks.json` (the recipe; the file name is kept) unless it has plain `build` and `preview` scripts. Only `yarn|npm|pnpm` running a plain vite, svelte-kit, next, astro, nuxt or remix script is accepted. Take the commands from the repo rulebook or package scripts; never invent them.
7. The board's Run button needs the worker (`agent-flow-board check watch`) or the service (`check service install|status|uninstall`; `service install --no-start` installs without starting, because a running worker holds the machine lock that `watch` also takes). It runs only folders where `check run` was used before or that are registered.
8. **A script run here with no board run (`--local`).** The board accepts only `M<n>` and `C<n>` keys for its own runs. A script with another key or one you do not want on the board runs with `agent-flow-board check run --local --org <org slug> --registration <NAME> <ITEM-REF> <KEY>` (or `--file <script in the scripts folder>`): same sandbox, preview, sign-in and guard rails, and no call to the board at all. Writes stay blocked. The last line is `RESULT <path>`; the pictures stay in that run folder until `check clear`. It needs the registration by name (or the script's `// afb-registration:` line) and stops at a changed pin; approve it with `check project pin <NAME> --org <org slug>`.
9. A script that only exists on the board is read with `agent-flow-board check pull <ITEM-REF> <CHECK-KEY> --org <org slug>`. It prints the text and its sha256 as data; `--accept-hash <sha256>` writes exactly that text. The board's saved script was written by someone with limited access: read all of it first, refuse anything that reads files, the network, the environment or the profile, and only then accept exactly what you read.

## Set up checks (guided, once per machine and repo)

This is what runs when the person said "set up checks" (or asked for a check) and `runner_status` or `check doctor` shows the bridge is missing, not connected or has no registration for this repo. It never runs on its own. The repo agent files (CLAUDE.md, AGENTS.md) are read first and win on ports, commands and what may be started. Setup edits no rule file (`/flow-align` does that) and starts no server of the person's.

**The agent does, in this order, with no question once the yes is given:**

1. Check what exists: `agent-flow-board` with no arguments (its usage lists `check`), `runner_status`, `agent-flow-board check doctor --json`. Skip every step that is already done.
2. Install the bridge when it is missing: say the exact command first, then run it (`npm install -g @agent-flow-board/bridge@latest`; it is a tool install, never a dependency of the repo, and it needs the Node version the package states).
3. Connect the organisation as "How a run works" step 2 says (`check connect`, then `tool_connection_approve`). When the token lacks the manage permission, say that one thing is the owner's and carry on with the rest.
4. Install the browser and repair what doctor lists: `check doctor --fix --json`, and again until `problems` is empty or the next step is the person's.
5. Register the repo folder: request a `roots` approval for the exact real path of the folder (`check approve --request`; a `register` approval is only for a live site or a registration being repointed), then `check roots add <dir> --approval <code>` and `agent-flow-board check project <NAME> --org <slug> --repo <dir>`. Take the build and preview commands from the repo rulebook or package scripts, never invent them.
6. For a web app the person runs locally, add the dev URL only when the rulebook allows a check on that server, as a separate registration with its own name and the same board project, never the name of the repo registration (that would replace it): `check project <NAME>-dev --org <slug> --board-project <KEY> --dev-url <origin with an explicit port>` (read-only; no `--start`, no `--allow-writes`, no edit of a `.env`; the host must be this machine). The port comes from the rulebook or the package scripts, never a guess. (example) a dev server on port 5173.
7. When the repo's preview runs on a throwaway database the bridge refuses a hand sign-in; the app then signs in with a recipe test user on every run or with a sealed test project, and this step is skipped. Otherwise ask for a `login` approval and run `check login <NAME> --org <slug> --approval <code>` in the background (step "Saved sign-ins" below), then tell the person one line: a sign-in window is open on their screen.
8. Run `check doctor --json` once more and `runner_status`, and say in one line what is ready and what still waits for the person.

**Only the person does:**

- Creates the account on the board address when they have none (the agent never creates an account for them; it needs its own named yes).
- Signs in once, in the window. That is the recommended way, because it works for every sign-in the site offers (password, emailed link, code, Google, two-factor) and no password ever passes through chat, a command line or a file.
- Alternative for an app with a plain email and password sign-in and a sealed test project: they put the test account in their own shell (`AFB_CHECKS_<NAME>_EMAIL` and `AFB_CHECKS_<NAME>_PASSWORD`) and the agent runs `check login <NAME> --org <slug> --seeded`. The agent never generates, echoes, writes or passes a password, and never puts one in `--why`.

**Other tools, as separate offers (one line each, only on a yes):** the flow skills themselves (`flow_skills`, as the connection's instructions say) and the editor status hooks (`editor_status_install`). They are not part of "set up checks".

## Registrations, an app folder, secrets, live sites

A registration names one repo folder (and optionally an app folder) or a live site for a board project. One board project can be built from more than one folder on the machine; each is its own registration, with its own recipe, saved sign-in, sealed secrets, kept builds and previews. Plans, items and checks stay in the one board project.

- `agent-flow-board check project <NAME> --org <slug> --repo <dir> [--app-dir web] [--board-project KEY] [--recipe]` registers a folder (it must be inside a folder the owner approved with `check roots`); `check project <NAME> --org <slug> --url <the site address> --extra-hosts <host names>` registers a live site (checks on a live site never write); `check project list|forget|pin`. `check project forget <NAME> --org <slug>` removes that registration's sign-ins, sealed secrets and kept builds (add `--remove` to drop the registration too). Pointing a registration at a different folder is refused until it has been forgotten. Two registrations never share a folder (use another clone or a `git worktree` for another branch), and a registration name never equals the board project key of another registration.
- A run chooses its registration in this order, never by guessing: the one the board names on the run (`check_run` `registration`), the one saved on the check (`check_save` `registration`), a `// afb-registration: NAME` line in the first 12 lines of the script, the board project's only registration. With several and none named it refuses (`REGISTRATION_REQUIRED`) and lists them; `REGISTRATION_MISMATCH` means the name serves another board project; `REGISTRATION_UNKNOWN` means no bridge holds it. `runner_status` lists the registrations an online bridge holds for the project. A pass closes a step only from the registration that was asked for.
- **Approvals (secrets, roots, live sites, .env, pictures, a sign-in window).** Ask for what you need with `agent-flow-board check approve --request --action <roots|register|secrets|adopt-env|pictures|login|dev> --target <name> --why "<one plain sentence>"` (or `--request-many "roots:<dir>;register:<NAME>@<host>;secrets:<org>/<NAME>"` for a whole plan, up to 20). The board approves at once: exit 0 prints one single-use code per entry (valid 10 minutes) that you pass as `--approval <code>`, and you say nothing to the owner. Never tell the owner to open a terminal, paste a command or make a code. The target is exact, and a code for another spelling does not work: `login` and `secrets` take `<org>/<NAME>`, `register` takes `<NAME>` (or `<NAME>@<host>` for a live site), `adopt-env` and `pictures` take `<NAME>`, `roots` takes the folder path, `dev` takes `<name>#<hash>` of the exact dev URL, start command and write allowlist (a registration that only names a read-only dev URL needs no `dev` approval; this flow never uses `--start` or writes). Exit 3 means still waiting (run the `--resume <ids>` line it prints); exit 1 means refused or expired: say so and stop. The text you write in `--why` is stored as plain text. A request that says the board could not be reached or the bridge is not connected to that organisation is yours to repair (connect as step 2 says). Then: `check roots add <dir> --approval <code>`, `check project <NAME> --org <slug> --adopt-env --adopt-env-approval <code>`, `check secrets import --project <NAME> --org <slug> --from <file> --keys A,B --test-ref <ref> --approval <code>` (a test Supabase project only; names are printed, never values), `check secrets list|forget`. A repo whose app needs a test Supabase project to start gets its keys this way: it needs the project ref and the owner's word that the env file points at a test project, which the bridge records; a project whose owner has not said so is a shared database you stop for. An app that signs in only by an emailed link needs its mail settings sealed the same way (`--keys POSTMARK_SERVER_TOKEN,POSTMARK_FROM_EMAIL,POSTMARK_MESSAGE_STREAM --test-inbox <address> --owner-said "<says the token is a test token>"`): the preview then mails only that one test inbox.
- A recipe may name sealed values as `{secret:NAME}`; they are given to the start only. A database value that points at the person's own database fails the run.
- **Saved sign-ins.** The owner signs in once in a window on their own computer, with whatever the site asks for (password, magic link, code, Google, two-factor): request a `login` approval (target `<org>/<NAME>`), then run `check login <NAME> --org <slug> --approval <code>` yourself, in the background (exit 4 window closed, 5 timed out), and tell the owner one line: a sign-in window is open on their screen. The command is yours to run; only the signing in is theirs. The session is saved sealed on that computer only. Another way for a plain password app: `--seeded` (from `AFB_CHECKS_<NAME>_EMAIL` and `_PASSWORD`). Never ask for a password in chat. On a repo registration, `check login` builds and starts the registration's own preview (sealed test project and mail fence) and opens the window on it. A preview on a throwaway database is refused, and `--seeded` needs the registration's sealed test project. An app that signs in by an emailed link: the owner asks for the link in the window, copies it from the test inbox and pastes it into the terminal, then presses Enter (never paste a link into chat; it is a one-time credential).
- **Profiles (role proofs).** `check login <NAME> --as <profile> --approval <code>` saves a second sign-in. A run uses it with `--profile <profile>` or a `// afb-profile: <profile>` line in the first 12 lines of the script. A named profile that is missing, damaged, expired or made on another project stops the run: read its sentence, run the login command it names yourself (with a new `login` approval) so the owner only signs in again in the window, and never fall back to another account. `check project profiles <NAME> --org <slug>` lists them (never a value); `check project forget <NAME> --org <slug> --profile <profile>` removes one.
- `check status|doctor --fix|clear` look after the bridge's own folders. Many runs at once share the machine's slots, browser and database pools, and kept dependencies and builds; nothing for you to set.

## Run codes and refusals

When a run ends with a **code**, apply its `fix` line and ask again, once. The codes are `PREVIEW_ENV_MISSING`, `PREVIEW_NEEDS_OWNER_URL`, `PREVIEW_HOST_UNREACHABLE`, `PREVIEW_PORT_BUSY`, `DB_NOT_THROWAWAY`, `TOOL_OFFLINE`, `TOOL_OUTDATED`, `TARGET_UNAVAILABLE`, `RUN_TIMED_OUT`, `SANDBOX_FAILED`, `DOCKER_DOWN`, `REGISTRATION_REQUIRED`, `REGISTRATION_MISMATCH`, `REGISTRATION_UNKNOWN`, and for a dev target `DEV_URL_UNREACHABLE`, `DEV_CROSS_HOST_REDIRECT`, `DEV_DB_NOT_THROWAWAY`, `DEV_APPROVAL_REQUIRED`, `DEV_PROFILE_MISSING` and `DEV_PROFILE_EXPIRED` (a phase peek answers any of them, and any failed dev run whatever its code, by using the preview and saying so in one line; never edit a `.env` to get past one; a dev run names the dev registration with `registration` next to `target` `dev`). If the same code comes back, stop and tell the person what the fix line says and what you tried. A busy port means something else holds it: find out what, and stop and ask before stopping a local server you did not start. `TOOL_OUTDATED`: upgrade with `npm install -g @agent-flow-board/bridge@latest`, then `agent-flow-board check doctor --fix --json`.

A command the bridge refuses with `Refused (<rule>)` is not an approval you may seek. Read the rule, fix the setting if the rule is about your setting (for example a build command that is not a plain package script), and if the rule is the point (a busy port, writes) say so and stop. A failing check is a finding to report, not a question.

One exception for a shared test database: when the person has imported its keys with `check secrets import` (which records the test project ref and their sentence), that import is their approval for running checks against that one test database. Writes to it, a different ref and any other shared database still stop for the person.

## What a check script may not do, and how to fix one fast

- **Blocked calls.** `page.addInitScript(...)` and navigating to `about:blank` are blocked. `check_save` refuses a script that holds one at once (`SCRIPT_BLOCKED`, with the fix) and saves nothing. Set state after the page has loaded with `page.evaluate`, and go straight to the page under test.
- **Time.** A check script may not run past 2 minutes; a longer one is stopped. Split a long measurement into several checks. A whole run is stopped after 40 minutes.
- **Writes.** A page's writes (POST, PUT, DELETE) are stopped and counted unless the site is made for testing. A write path is proved with a write-enabled run on this machine, never on a live site.
- **A signed-in registration.** A run needs a registration with a saved sign-in. Without one the page is a logged-out 404. Check the registration is signed in (`check status --json`, `doctor`) before the first run.
- **Data the page needs.** A page that shows a sample event, a list or a setting needs that data to exist in the throwaway database. Confirm it is there before you write the check.
- **Several runs at once.** A run that shared the machine with another run shows `sharedCpu: true` in `check_status`: its time is not a speed measurement. Run a speed comparison alone (`check watch --parallel 1`), once, and say so with the number.
- **Fixing a saved check.** Read it with `check_get`, change it with `check_save` and `edit: { old, new }` (the old text must appear exactly once). Do not resend the whole script for a small fix. Update the local file with the same change.
- **Reading the result.** `check_status` answers with the newest run of each check in short form; ask for `detail: true` only when you need the files.

## Prove the risky path first, and write the check from facts

- **The write path and the dialog that closes first.** Before the read-only checks, prove the riskiest interaction (a form that writes, a reset or confirm dialog, anything that must close with Escape, the X and a click outside) with a write-enabled run on this machine. Do not report the work as done before that run has passed.
- **Facts before a check.** Take every number, label and button from the real source (the component, the data, the running page), never from a comment or from memory. A guess found by a failed run costs minutes.
- **One measurement, alone.** A speed or size comparison is run once, alone, on a quiet machine, and the number is reported with that fact.
- **Do not widen the work.** Run only the checks the plan has, the automatic check, or what the user asked for.

## Screenshots, compare, inspect, dev-server checks

A check's screenshots are its evidence: the bridge takes them while the check runs, and the board shows them on the item's Checks tab (the newest run, earlier runs and a full size view). To prove how a screen looks, write a check that opens it at the widths and in the colour modes that matter and takes a screenshot of each; read the result with `check_status`.

- **Compare against a hosted mockup:** `agent-flow-board check compare --mockup <id>[@version] --registration <name> --server <url> --org <slug> --screens <s1,s2> --states <t1,t2> --widths 390,1280 --manifest <pairs.json> --brief <design-brief.md> --item <ref> --key <KEY>` captures both sides, measures layout and style parity, and attaches `compare-diff.json` and picture pairs to the run. A mockup that carries a contract gives compare its pairs, its free lines and how each state is reached; `--manifest` is then only for what you add. Motion is measured as well (durations, easing and presence, 20 ms of tolerance); `--reduced-motion` opens both sides with the reduced-motion preference.
- **Inspect DOM measurements:** `agent-flow-board check inspect <registration> --org <slug> --screen <S> --state <T> --width <W>` against the running app (and `agent-flow-board mockup inspect` against the mockup).
- **Dev-server checks (`dev` target)** probe the local dev server only with the owner's dev approval (`DEV_APPROVAL_REQUIRED` otherwise); never send writes against a running dev server without an isolated throwaway copy. Early and full runs also capture versioned stock visual checks (`cls`, `tap-targets`, `sideways-scroll`, `button-chrome`, `contrast-pairs`, `skeleton-height`, `focus-visible`, `reduced-motion`, `console-errors`).
- **Windows and Git Bash:** keep bracketed route paths quoted (such as `'src/routes/[org]/+page.svelte'`), pass `MSYS_NO_PATHCONV=1` when running CLI commands with Unix-style flags or paths under Git Bash, and keep check and doc scripts on LF line endings even if Git `core.autocrlf=true` is enabled.

## Limits to say out loud

- A pass closes a step only when the bridge could tie the run to a commit (the project's repo folder). Otherwise the board records it as unverified.
- Every run makes its own private copy of the repo, its own port and its own throwaway database on 127.0.0.1; they go when the run ends. Dependencies and builds kept from an earlier run are copied in, never shared. `check doctor --fix` removes what a dead run left, and `check clear` removes what the bridge recorded, by name, and nothing else.
- `runner_status` shows `capacity`. A bridge that is full still queues your run and runs it when a slot is free.
- Targets and limits come from the project's environments on the board and from the repo rulebook. A target the environments mark as live is never a check target.
- Every change you make to the bridge's setup is written to its audit chain, and the board keeps the chain's length. Do not edit that log.
- The few questions the bridge asks when it sets a project up are answered from the repo rulebook, the recipe and the project's environments. Ask the person only what those cannot settle.
